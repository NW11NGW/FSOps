## Solution layout

FSOps is a single .NET solution (`FSOps.sln`) with a React frontend alongside it:

| Project | Responsibility |
|---|---|
| `src/FSOps.Core` | Domain model, money handling, route planning, and finance calculations. Airlines, routes, aircraft, flights, pilots, and the entities and pure logic that drive them — see [FSOps.Core areas](#fsopscore-areas). No dependency on ASP.NET Core, EF Core, or SimConnect — this project is plain C# so it can be unit tested in isolation. |
| `src/FSOps.Data` | Persistence. Entity Framework Core mapping of the domain model onto SQLite, entity configurations, world data import, and the `FsOpsDbContext` used by the server. |
| `src/FSOps.Sim` | The sim abstraction and its two implementations: `SimConnectSource`, which wraps `CTrue.FsConnect` to read live aircraft state from a running copy of MSFS, and `FakeSimSource`, which replays a recorded flight from a JSON script with no simulator needed. Both implement the same `ISimSource` interface (see [Sim abstraction](#sim-abstraction)). |
| `src/FSOps.Server` | The ASP.NET Core host. Exposes the REST API (see [API endpoint surface](#api-endpoint-surface)) and SignalR hubs, runs the background services that pump sim telemetry and drive flight tracking (see [Simulator connection and the telemetry pipeline](#simulator-connection-and-the-telemetry-pipeline)), post the monthly billing cycle (see [The monthly billing cycle](#the-monthly-billing-cycle-economyclockservice)), and resolve virtual pilots' scheduled flights on the wall clock (see [Virtual pilots and wall-clock resolution](#virtual-pilots-and-wall-clock-resolution-virtualflightresolverservice)); also runs `ReservationReconciler` once on every startup, before those hosted services start, to repair any aircraft left both reserved-for-player and scheduled by a database written before that rule existed (see [Aircraft reservation](#aircraft-reservation-the-two-way-gate-and-reservationreconciler)); wires everything together via dependency injection, and serves the built frontend as static files. |
| `src/fsops-web` | The React + TypeScript frontend, built with Vite and styled with Tailwind CSS and shadcn/ui, with MapLibre GL for the route-network and live-flight maps. Runs entirely in the browser against the local server. |
| `tests/FSOps.Core.Tests` | xUnit tests, focused on `FSOps.Core`'s domain, planning, and flight-tracking logic (phase state machine, landing quality, aircraft-type matching, flight numbering). |
| `tests/FSOps.Server.Tests` | xUnit tests for server-level behaviour that needs a database, chiefly round-trip route pairing and airline-summary route counting. |

## FSOps.Core areas

`FSOps.Core` is organised into a handful of focused areas rather than one flat namespace:

| Area | Contents |
|---|---|
| `Entities/` | The domain model: `Airline`, `Route`, `FleetAircraft`, `Flight`, `FlightEvent`, `Pilot`, `PilotSchedule`/`PilotScheduleEntry`, `Loan`, `Lease`, `LedgerTransaction`, `MaintenanceEvent`, `EconomyState`, `Airport`, `Runway`, `AircraftType`, `UserSettings`, and the shared enums (strategy profile, units, currencies, statuses). `Flight.Revenue`/`TotalCost` are a read-time cache of what's actually been posted to `LedgerTransaction` for that flight - never the source of truth themselves (see [Append-only ledger](#append-only-ledger)) - and `Flight.RevenuePosted` is the idempotency gate that stops a retry or crash rehydration posting a flight's ledger lines twice. `FleetAircraft.ReservedForPlayer` is the sole, hard gate between the player and the virtual-pilot scheduler - see [Aircraft reservation](#aircraft-reservation-the-two-way-gate-and-reservationreconciler). `PilotSchedule` is the aggregate root for one virtual pilot's standing weekly schedule (created lazily, on first save), and carries `AutoSuspendOnMaintenance` (default `true`) - whether an occurrence whose aircraft is grounded for a check is recorded as the `FlightStatus.Suspended` value (distinct from `Skipped`/`Cancelled`, and never fee-bearing) rather than skipped or cancelled outright; `PilotScheduleEntry` is one leg in it - a day of the week, a departure time (UTC), a directional route leg, and the fleet aircraft that flies it. There's no end date: the week itself is the repeating unit. `EconomyState.AwaySummaryLastViewedUtc` is a cursor distinct from the billing/schedule watermarks (see below) - it tracks only how much of the ledger/flight/maintenance history has been shown to the player in a "while you were away" summary, and only `POST /away-summary/acknowledge` ever advances it. |
| `Economy/` | The economy engine: `EconomyConfig` (every tuning constant for one resolved playstyle) and `EconomyConfigCatalog` (loads `economy-config.json` once and resolves the two playstyle-specific configs from it - see [Playstyles and EconomyConfigCatalog](#playstyles-and-economyconfigcatalog)), `ReferenceFareCalculator`, `DemandCalculator` (city-pair passenger pool from catchment/distance/season/day/reputation), `FareDemandModel` (the anti-exploit fare/load-factor/revenue curve - see [Fare setting and demand response](guides/user-guide.md#the-economy-simulation) in the user guide), `FuelPricing` (per-airport, per-day fuel price), `TankeringAdvisor` (whether uplifting extra fuel here to skip a pricier refuel later would pay off - see [Persistent fuel and tankering](#persistent-fuel-and-tankering)), `MaintenanceScheduler` (A/C-check triggering, downtime and used-aircraft starting wear - see [Maintenance scheduling](#maintenance-scheduling)), `ReputationCalculator` (advances `Airline.ReputationScore` by one flight's outcome - see [Reputation and pilot skill](#reputation-and-pilot-skill)), `FlightCostCalculator` (weight- and size-based landing/handling/parking/passenger/turnaround fees, maintenance accrual, crew cost), and `FlightEconomicsCalculator`, which ties all of the above into one itemised `FlightEconomicsResult` for a single flight. Pure - no database, no I/O. `FSOps.Server.Services.FlightEconomicsPoster` is the only place that result becomes real `LedgerTransaction` rows: fuel is posted at flight start, only for what's actually uplifted (see [Persistent fuel and tankering](#persistent-fuel-and-tankering)); every other line posts on completion, gated on `Flight.RevenuePosted` for idempotency, and skipped entirely for a slew/position-jump-flagged sector rather than computed and discarded. Recurring monthly billing (lease, salary, insurance, loan amortisation) is a separate background service, `FSOps.Server.Services.EconomyClockService` - see [The monthly billing cycle](#the-monthly-billing-cycle-economyclockservice). A virtual pilot's completed flight goes through this exact same pipeline - see [Virtual pilots and wall-clock resolution](#virtual-pilots-and-wall-clock-resolution-virtualflightresolverservice). |
| `Flights/` | Flight tracking's pure domain logic: `FlightPhase` (the ten-phase enum), `FlightPhaseThresholds` (the speed/altitude/timing constants that drive phase transitions), `FlightPhaseStateMachine` (advances phase-by-phase from telemetry samples, captures OOOI and touchdowns, and restores itself from a stored event history), `LandingQualityCalculator` (runway-centreline deviation), `FlightIntegrityMonitor` (elevated simulation rate, slew, and position-jump detection - see [Append-only ledger](#append-only-ledger)), and `AircraftTypeMatcher` (family-level, informational-only aircraft matching). See [Flight-phase detection and landing quality](#flight-phase-detection-and-landing-quality). |
| `Routes/` | `FlightNumberGenerator` — deterministic odd/even outbound/return flight-number pairing per airline, pure and side-effect free. |
| `Scheduling/` | `WeeklyOccurrenceCalculator` (pure date math: given a day-of-week and a time of day, finds the most recent occurrence at or before a given instant, or every occurrence in a window - the shared timing primitive both the resolver and the live operations map build on), `PilotScheduleValidator` (the aircraft-per-duty-day invariant - every entry for one pilot on one day must reference the same `FleetAircraftId`, checked and failed fast before anything else - plus geographic continuity, aircraft double-booking across pilots, minimum turnaround, pilot rest/duty-length limits, and refusing a reserved-for-player aircraft outright, all against a proposed set of schedule entries, cyclically across the week), `VirtualPilotPerformanceCalculator` (a pilot's weekly sectors/hours/revenue/cost summary shown on the Pilots page), and `PilotSkillCalculator` (derives `Pilot.SkillRating` from hours flown and idle time - see [Reputation and pilot skill](#reputation-and-pilot-skill)). Pure, no database. See [The weekly schedule builder](#the-weekly-schedule-builder-aircraft-per-duty-day). |
| `Money/` | `CurrencyCatalogue` (the supported-currency list, each with a fixed display rate against the GBP-pegged base unit) and `MoneyFormatter` (base-unit → display-currency conversion and formatting). See [Money is stored in a single base unit](#money-is-stored-in-a-single-base-unit). |
| `Planning/` | Route preview math: `GreatCircle` (distance/bearing), `CruiseAltitudeSelector`, `BlockTimeEstimator`, `BlockFuelEstimator` (also used by `TankeringAdvisor` to price the extra weight a tankered sector would burn), composed together by `RoutePreviewCalculator` into one preview result plus validation warnings - including the suggested fare, sourced from `Economy/ReferenceFareCalculator` (the same figure the demand engine anchors to - see docs/PLAN.md "Status after the fuel-honesty fix"). Pure, deterministic, no I/O. |
| `Finance/` | `LoanCalculator` (amortising loan monthly-payment math and the monthly interest/principal split `EconomyClockService` applies), `LoanRateCalculator` (the only code allowed to price a loan's interest rate - risk-based, scaling from the playstyle's base rate to its cap as the loan consumes more of the airline's borrowing capacity), `LoanEligibilityCalculator` (borrowing capacity itself: 30% of trailing 30-day net operating cash flow), `AircraftDepreciationCalculator` (an owned aircraft's sale value - depreciates with condition, cycle wear, and a grounded-for-maintenance penalty), `LeaseTerminationCalculator` (pro-rata charge for the part of the current 30-day period used, plus a flat early-termination fee), and `LoanSettlementCalculator` (full-payoff quote with an early-settlement fee, and overpayment - which reduces principal and shortens the term without changing the monthly payment). The last three back `FleetDisposalEndpoints`/`FinanceEndpoints`'s quote-then-confirm actions - see [Getting rid of an aircraft, and settling a loan](#getting-rid-of-an-aircraft-and-settling-a-loan-the-quote-then-confirm-pattern). `LoanCalculator`/`LoanRateCalculator`/`LoanEligibilityCalculator` are used for both the startup loan at airline creation (now capped at a flat per-playstyle `EconomyConfig.Loan.MaxStartingLoanPrincipal`, since a brand-new airline's zero trading history makes the cash-flow-based mid-game cap resolve to zero) and a mid-game loan from the Fleet page. |
| `Airlines/` | `AircraftRegistrationGenerator` (country-appropriate tail number generation for a newly leased aircraft). Starting capital, lease deposit and starting pilot salary used to live here as `AirlineCreationDefaults`; they now live in `Economy/EconomyConfig.AirlineStartup` instead, alongside every other tunable economy figure, so airline-creation balance can be retuned the same way as everything else - see the `Economy/` row above. |
| `Airports/` | `AirportSearchRanking` and `AirportSizeCategoryMapper`, used by airport search and by the home-base-suitability check in airline creation. |
| `AppPaths.cs` | Runtime resolution of every path FSOps writes to. See [App paths](#app-paths-no-hardcoded-filesystem-paths). |

## Request and data flow

There are two flows through the system: user-driven requests from the browser, and live telemetry from the simulator.

**Browser-driven flow:**

```
Browser SPA (fsops-web)
    │
    ├── REST calls  ──────────────► /api/v1/*
    └── live updates ◄────────────► /hubs/live  (SignalR)
                                        │
                                        ▼
                              Backend services (FSOps.Server)
                                        │
                                        ▼
                              Domain / economy logic (FSOps.Core)
                                        │
                                        ▼
                              EF Core (FSOps.Data) ──► SQLite
```

The frontend talks to the backend two ways: versioned REST endpoints under `/api/v1` for requests with a clear request/response shape (creating an airline, adding a route, and so on), and a SignalR hub at `/hubs/live` for anything that needs to push to the browser without being asked — a heartbeat, live flight telemetry, and flight-completion/needs-resolution notifications.

**Simulator-driven flow:**

```
MSFS 2024
    │
    ▼
SimConnect  ──────────────► FSOps.Sim (telemetry channel)
                                        │
                                        ▼
                              Flight tracker (FSOps.Server / FSOps.Core)
                                        │
                                        ▼
                              Broadcast over /hubs/live ──► Browser SPA
```

`FSOps.Sim` owns the SimConnect connection and turns raw sim variables into a telemetry stream. `SimTelemetryService` (`FSOps.Server`) pumps that stream at the sim's own sampling rate, feeding `FlightLifecycleService` full-rate for accurate phase detection while throttling what it broadcasts over `/hubs/live` to twice a second, so the browser gets smooth live updates without every sim frame crossing the wire. `FlightLifecycleService` is where telemetry becomes domain logic — advancing the flight-phase state machine, capturing landing quality, and persisting the append-only event log a flight is built from (see [Flight-phase detection and landing quality](#flight-phase-detection-and-landing-quality) and [The append-only flight event log and crash recovery](#the-append-only-flight-event-log-and-crash-recovery)) — before broadcasting live updates back out over the same hub the browser is already listening on.

## Design principles

### Local-first, structured to move online later

FSOps runs entirely on your machine today — SQLite on disk, no account, no server to talk to. But it's structured so that moving parts of it online later (sync across machines, a hosted backend, multi-user features) is a matter of extension rather than rewrite:

- **GUID primary keys** throughout the domain model, rather than auto-incrementing integers, so records generated locally on different machines never collide.
- **UTC timestamps** everywhere, so time comparisons are never ambiguous once data starts moving between machines in different time zones.
- **Append-only event and ledger tables** (see below) rather than rows that get overwritten in place, which is what makes eventual sync or replay tractable.
- **A versioned API** (`/api/v1`) from day one, so the contract between frontend and backend can evolve without breaking older clients.
- **An auth abstraction** (`ICurrentUser` in `FSOps.Server`) that every endpoint and query is expected to depend on instead of reading identity directly off the request. Locally there's only ever one user, but this means introducing real authentication later is a dependency-injection change, not a rewrite of every endpoint.
- **Every row scoped by owner.** `OwnerUserId` on account-level records (`Airline`, `UserSettings`) and `AirlineId` on everything that hangs off an airline (routes, fleet, pilots, ledger transactions, flights) mean every query already filters by who owns what. Locally that's always the same single user, but the schema is already shaped for multiple users sharing one database once real auth lands.

### Money is stored in a single base unit

Every amount that touches money — `LedgerTransaction.Amount`, an aircraft's purchase price, a route's fare, a loan's principal — is stored in one fixed base currency unit (GBP-pegged; see `CurrencyCatalogue.BaseCurrencyCode` in `FSOps.Core.Money`), never in whatever currency the user happens to have selected.

Display currency is purely a read-time transform: `MoneyFormatter.ConvertFromBase` multiplies a base-unit amount by the selected currency's fixed `DisplayRate` and formats it with that currency's symbol and decimal places. Nothing is ever converted the other way and written back — a user switching their display currency in settings changes what every screen shows, never what's stored. This also means display rates don't need to be fetched or kept in sync with real exchange rates; FSOps is a game economy, not a forex simulator.

### Append-only ledger

Your airline's cash balance is never stored as a single mutable number that gets incremented and decremented in place. Instead, every financial event — a ticket sale, a fuel bill, a lease payment, a loan drawdown, starting capital — is written as its own row in an append-only `LedgerTransaction` table. The cash balance the API and UI show is always derived as **`SUM(LedgerTransaction.Amount)`** for the airline, computed at read time, rather than read off a stored column.

`FlightEvent` (the phase-by-phase record of a tracked flight) follows the same append-only rule for the same reason: a historical record that's only ever added to is self-auditing — nothing is silently overwritten, and any derived value can be reconstructed or verified independently just by re-reading the log. See [The append-only flight event log and crash recovery](#the-append-only-flight-event-log-and-crash-recovery) for how this is put to use.

This costs a bit of query overhead — SQLite's EF provider can't translate `Sum()` over `decimal` into SQL, so the (small, per-airline) set of amounts is pulled into memory and summed there — in exchange for a system where the financial history can't drift out of sync with how it got there.

### App paths: no hardcoded filesystem paths

FSOps installs into `Program Files`, which is read-only for standard users, so nothing may ever be written next to the executable. Every path FSOps writes to — the SQLite database, log files, and any future config — is resolved at runtime through `AppPaths` (`FSOps.Core.AppPaths`), which resolves everything under the current Windows user's `%LOCALAPPDATA%\FSOps\` and creates directories on first access:

- `AppPaths.DataDirectory` → `%LOCALAPPDATA%\FSOps\`
- `AppPaths.DatabasePath` → `%LOCALAPPDATA%\FSOps\fsops.db`
- `AppPaths.LogsDirectory` → `%LOCALAPPDATA%\FSOps\logs\`

No file path is ever hardcoded elsewhere in the codebase — everything goes through `AppPaths`. That's what makes FSOps work correctly wherever it's installed and for whichever Windows account is running it, without an installer needing to set permissions on a shared location.

### Deterministic, testable planning logic

Route planning — distance and bearing, cruise altitude selection, block time and fuel estimation, fare suggestion — lives in `FSOps.Core.Planning` with no dependency on the database, the web framework, or the simulator. Given the same inputs, it produces the same outputs every time. That determinism is what makes it practical to unit test thoroughly in `FSOps.Core.Tests`: planning behaviour can be verified in isolation, without spinning up a server or a database, and without MSFS anywhere in the loop. The economy engine (`FSOps.Core.Economy`) follows the same pattern — demand, fares, fuel pricing and flight costs are all pure functions of their inputs, with even fuel price's day-to-day drift coming from a hand-rolled stable hash rather than a stateful random number generator, so the exact same (airport, date) always prices identically. The one input that isn't fully pinned down by the caller is *when*: `DemandCalculator` reads the real clock (`DateTimeOffset.UtcNow`) for season and day-of-week, so the same route genuinely does price differently depending on what day you fly it — that's intentional (see [The economy simulation](guides/user-guide.md#the-economy-simulation) in the user guide), not a break in determinism, since every test pins the date explicitly rather than relying on the clock.

### Sim abstraction

`FSOps.Sim` sits behind `ISimSource` — a small interface (connection state, the currently loaded aircraft, and a channel of telemetry samples) that the rest of the app depends on, not any concrete implementation directly. Deliberately, no SimConnect-specific type is allowed to leak across that interface. That means a fake or replay-based telemetry source can stand in for MSFS entirely, which is what makes it possible to develop and test flight tracking, phase detection, and landing scoring without the simulator running at all, and without a human re-flying the same approach over and over to test a bounce-detection edge case.

`FakeSimSource` is that replay source: it plays back a scripted flight from a JSON file (the bundled default is a roughly 93-minute EGKK→LEBL sector) at a configurable time-compression factor, optionally looping. `SimConnectSource` is the real adapter, wrapping the `CTrue.FsConnect` library. Which one runs is a plain startup switch — the `sim` command-line argument (or `Sim:Source` in configuration) selects `fake` for the replay source; anything else, including nothing at all, talks to a real, running copy of MSFS. This is what the whole test suite and most day-to-day development runs against, rather than requiring MSFS to be open.

## Simulator connection and the telemetry pipeline

**Connecting.** `SimConnectSource` runs a connection loop for the lifetime of the process: each attempt creates a fresh `FsConnect` instance, calls `Connect()`, and only then registers FSOps' telemetry and aircraft-identity data definitions, before waiting for either a connected or disconnected signal. That ordering is deliberate and was previously a real bug: `RegisterDataDefinition` forwards straight to the underlying SimConnect handle, which doesn't exist until `Connect()` has actually run — registering first silently failed to reach a live MSFS 2024 session. The fix (registering after connecting, not before) has been verified against live MSFS 2024 with a Fenix A320. If a connection attempt fails or drops, it's disposed and retried after a fixed interval (5 seconds). This is why FSOps doesn't need restarting just because MSFS wasn't ready the first time — it keeps trying on its own for as long as it's running.

**Sampling rate.** Telemetry is read at an adaptive rate rather than a fixed one: roughly 5 Hz in normal flight, stepping up to essentially every sim frame once the aircraft is below 2,000 ft AGL, where the extra fidelity matters for accurately catching the moment of touchdown. A small hysteresis band (300 ft) around that threshold stops the rate from flapping back and forth near the boundary.

**What's read.** Each sample carries position (latitude/longitude), altitude (both MSL and AGL), indicated airspeed, ground speed, vertical speed, true and magnetic heading, on-ground state, engine-running state, parking brake state, G-force, the instantaneous touchdown vertical velocity simvar (only meaningful at the moment of ground contact — this is what landing-rate scoring is built on), and total fuel weight. The aircraft's title and ATC model/type are fetched separately, once per connection or aircraft change rather than every sample, since they don't change mid-flight.

**Pushing it live.** `SimTelemetryService` (`FSOps.Server`) reads the full-rate sample stream and does two things with it: it hands every sample to `FlightLifecycleService` for phase detection (see below), and it broadcasts a throttled subset — at most once every 500 ms (2 Hz) — over the `/hubs/live` SignalR hub as a `telemetry` message, carrying timestamp, position, altitude, speeds, headings, on-ground state, and connection state. The throttling keeps the browser's live view smooth without pushing every sim frame across the wire; the full-rate stream still reaches the phase state machine so a fast transition (like the instant of touchdown) is never missed just because the broadcast rate is lower.

`GET /api/v1/sim/status` exposes the same connection state on demand — current state, which source is active, the last-seen aircraft title, and the last sample's timestamp — for anything that wants to poll rather than subscribe (the Fly screen's readiness checks use this, alongside the live hub).

## Flight-phase detection and landing quality

A tracked flight moves through ten phases, in order, with one deliberate exception: **Preflight → Taxi out → Takeoff roll → Climb → Cruise → Descent → Approach → Landed → Taxi in → Shutdown**, except that a go-around sends the state machine back from Landed to Climb rather than continuing forward. `FlightPhaseStateMachine.Advance()` runs this transition logic once per telemetry sample, driven entirely by thresholds in `FlightPhaseThresholds` — ground speed crossing 2 kt or 40 kt, vertical speed settling within a 300 fpm band for 20 seconds (levelling into cruise) or descending past -300 fpm for 15 seconds (starting a descent), altitude dropping below 3,000 ft AGL while descending (entering approach), and so on. All of this is timed from the samples' own timestamps, never wall-clock time, which is what makes the whole thing replayable and deterministic in tests.

OOOI times (out/off/on/in) are captured as by-products of specific transitions: **out** when taxi begins, **off** when the aircraft becomes airborne, **on** at the first ground-contact after the approach, **in** once engines are off and the parking brake is set at the end of taxi-in.

**Touchdown and landing quality.** Every ground-contact event while approaching or already landed registers a touchdown record: touchdown rate in feet per minute (converted from the sim's raw touchdown-velocity simvar), and G-force — tracked as a peak over the few seconds immediately following contact, not just the instantaneous value at the moment of contact, so a hard bounce a beat after touchdown is still captured. A landing that bounces (leaves the ground only briefly before settling) keeps accumulating touchdown records against the same landing; one that stays airborne for more than a few seconds is reclassified as a go-around instead, clearing the touchdown records and sending the phase machine back to Climb. Centreline deviation is computed separately, once a flight finalises: `LandingQualityCalculator` picks the runway at the arrival airport whose heading is closest to the touchdown's track, then measures the perpendicular distance from the touchdown point to that runway's centreline.

**Aircraft-type matching.** `AircraftTypeMatcher` checks the sim's reported aircraft title and ATC model against a route's expected aircraft type using a stored list of regular expressions per family (so a 737-800 and a 737-700 both match a "B737 family" pattern without special-cased logic — the permissiveness lives in the stored pattern, not the matcher). This check is deliberately incapable of ever blocking or costing anything: an unparsable pattern list or a broken regex is treated as "no match" rather than as an error, and the result is stored purely as an informational flag on the flight, never consulted by anything that touches money.

## The append-only flight event log and crash recovery

Every meaningful thing that happens during a tracked flight — a phase change, a touchdown, a periodic position snapshot (every 15 seconds, so a flight's track can be reconstructed even between phase changes), an aircraft-type mismatch — is written as its own row to the `FlightEvent` table, following the same append-only rule as the financial ledger (see [Append-only ledger](#append-only-ledger)): never updated, never deleted. `FlightLifecycleService` queues these events in memory and writes them off the telemetry hot path in small batches, so persisting to SQLite never competes with processing the next incoming sample.

This log is what makes a tracked flight survive FSOps or MSFS crashing partway through. On startup, if a flight is still marked in progress, `FlightLifecycleService` loads its full event history and replays it through `FlightPhaseStateMachine.RestoreFrom()` — reconstructing phase, OOOI times, and any touchdowns already recorded, purely from the stored events, with no reliance on any in-memory state that didn't survive the crash. It then waits for the simulator to reconnect near the flight's last known position (within about 5 nm) for up to 30 seconds. If that happens, tracking resumes as if nothing happened. If it doesn't, the flight is marked **Interrupted** rather than silently resumed or abandoned — surfaced to the user as a flight that needs resolving (see [Ending a flight, and what happens if it gets interrupted](guides/user-guide.md#ending-a-flight-and-what-happens-if-it-gets-interrupted) in the user guide), where they can wait for reconnection, complete the flight with estimated figures, or abandon it outright. Nothing about a flight's already-recorded history is ever lost by this process — it's exactly what the replay is built from.

## Playstyles and EconomyConfigCatalog

Every airline is created with a permanent `AirlinePlaystyle` (`Casual` or `TrueLife` - see [Playstyles](guides/user-guide.md#playstyles) in the user guide) chosen once at founding, with no update path afterwards. `EconomyConfigCatalog` is what makes this work without branching logic scattered through the economy engine: at startup it parses `economy-config.json` once, reads the file's shared base fields (fares, demand, fuel, the maintenance cycle, the used-aircraft market - identical for every airline) plus two small `casual`/`trueLife` override blocks (starting capital, lease deposit term, every aircraft type's lease rate, monthly insurance, maintenance downtime, and the loan rate base/cap), and resolves two fully-merged `EconomyConfig` instances, validating each the same way a single config would validate itself.

A playstyle is a **named set of overrides, not a code path** - nothing downstream ever asks "is this airline Casual or True-life?" Callers resolve the right `EconomyConfig` once (`economyConfigCatalog.Get(airline.Playstyle)`, typically right after loading the airline that owns the request) and hand it to the same economy engine every airline uses. This is also why `Program.cs` deliberately does **not** register a flat `EconomyConfig` singleton in DI - one existed briefly during development and was removed on purpose: every config-derived figure must be resolved per-airline through the catalogue, and a constructor that fails to resolve one is meant to fail loudly (inject `EconomyConfigCatalog` instead) rather than silently fall back to a config that might be the wrong playstyle for the airline in scope.

## The monthly billing cycle: EconomyClockService

`EconomyClockService` is a `BackgroundService` that posts the fixed monthly costs a flight-by-flight economy never touches: one lease payment per active `Lease`, one salary line per `Pilot`, one insurance line per fleet aircraft (looked up live from `EconomyConfigCatalog` against the owning airline's playstyle, since insurance is the one figure that isn't already baked into a stored row), and the amortised interest/principal split (`LoanCalculator.ApplyMonthlyPayment`) for every outstanding `Loan`. It runs once immediately at startup - so a catch-up after being closed happens right away rather than up to a minute later - and then every 60 seconds after that.

A "month" is exactly 30 days of wall-clock time from `EconomyState.LastProcessedUtc` (a single-row watermark), not a calendar month. Each pass advances the watermark one 30-day period at a time, posting that period's charges and moving the watermark past it in the *same* `SaveChangesAsync` call - so a period's ledger rows and the watermark that says "this period is done" either both land or neither does; a crash mid-catch-up can lose at most the not-yet-committed remainder of that pass, never post a half-charged or double-charged month. A `SemaphoreSlim` also serialises overlapping calls within the process, the only place two "ticks" could ever race.

Two integrity properties matter here, both deliberate:

- **Catch-up is bounded.** If FSOps was closed for a long time, one pass posts at most 24 periods (about two years) before yielding back to the next 60-second tick - an unbounded closure doesn't mint an unbounded burst of charges in a single pass, but it does still catch up fully within a handful of passes.
- **The watermark only ever moves forward, and never past the current clock reading.** A clock reading that comes back *before* the watermark (a wound-back system clock) is treated as a backwards jump: nothing is processed, the watermark doesn't move, and it's logged rather than silently absorbed. Winding the clock *forward* can't mint more than the 24-period cap per pass either. This is what makes the wall-clock model resistant to clock manipulation in either direction.

## Persistent fuel and tankering

`FleetAircraft.FuelOnBoardKg` is a real, persisted quantity - the aircraft's tank state carries forward between flights rather than resetting every sector. `FlightEndpoints.StartAsync` reconciles it against reality at the start of every flight:

- **With a recent telemetry sample** (the sim is connected and has reported within the reconciliation window), that reading is trusted as ground truth. `FuelUpliftDetector` classifies the change since the last tracked figure: a rise is charged as an uplift, at the departure airport's price; a fall is silently absorbed as consumed, never credited. This is what catches fuel that changed while FSOps wasn't watching - a sim restart, a menu fuel set, or the pilot topping off the tank before pressing Start flight.
- **With no recent sample** (sim not connected, or the flight will only ever be completed manually), FSOps falls back to a conservative assumption: top up to exactly this sector's own `ChargedFuelKg` (trip + taxi + contingency - not the alternate/reserve allowance) if the tank doesn't already hold that much.

Either way, a sector flown on fuel already in the tank - most commonly the return leg of a route just flown outbound - posts no `Fuel` ledger line at all. `FlightLifecycleService` keeps `FuelOnBoardKg` in sync with live telemetry for the rest of the flight and writes the final in-tank figure back on landing/abandonment.

`TankeringAdvisor` (`FSOps.Core.Economy`) is a pure, advisory-only calculator surfaced on the Fly screen's flight brief: it compares uplifting extra fuel now (at the departure price, but burning a little more of it per the `Fuel.CostOfCarryRatePerHour` config constant - roughly 3% of the *extra* mass carried, per hour airborne) against buying nothing extra and refuelling at the destination's price, and flags if the extra fuel would exceed the aircraft's MTOW. It never touches the ledger itself. One documented gap: `FlightCostCalculator.LandingFee` is keyed off the aircraft type's fixed `MtowTonnes`, not the aircraft's actual operating weight at landing, so carrying tankered fuel does not raise the landing fee it will pay - cost-of-carry burn is the only counterweight the model can currently apply.

## Maintenance scheduling

`MaintenanceScheduler` (`FSOps.Core.Economy`) is pure arithmetic: given a fleet aircraft's current hours/condition and the flight hours it has just flown, it decides whether an A-check (every 500 airframe hours) or a C-check (every 4,000) fires, what it costs, how long it grounds the aircraft, and the new hours/condition either way. Condition decays a small, configured amount per flight hour; an A-check partially restores it (35 points, capped at 100) while a C-check always resets it to 100 outright, since the shipped config makes the C-check interval a whole multiple of the A-check interval, so a C-check-due moment is always also an A-check-due moment and the two cycles reset together rather than scheduling a redundant A-check moments later. Downtime hours are the one maintenance figure that differs by playstyle (Casual: a handful of hours for an A-check, about a day for a C-check; True-life: about a day, and about a fortnight, respectively) - everything else about the cycle (interval hours, cost, condition decay/restore) is identical for both.

`MaintenancePoster` (`FSOps.Server.Services`) is the single call site both flight-completion paths (the live telemetry path in `FlightLifecycleService` and the manual-completion path in `FlightEndpoints`) use to apply the scheduler's result: it bumps `AirframeHours`, and if a check triggered, grounds the aircraft (`FleetAircraftStatus.InMaintenance`, with `GroundedUntilUtc` set so the UI can say not just "in maintenance" but until when), writes a `MaintenanceEvent` row, and posts the cost as a `LedgerTransaction`. `MaintenanceReleaser` is the wall-clock counterpart: rather than a dedicated background timer, it's called lazily at the top of every endpoint that reports or depends on fleet availability (`GET /fleet`, `GET /flights/options`, `POST /flights/start`) and releases any aircraft whose `GroundedUntilUtc` has already passed, so the very next request after a grounding period ends always sees it correctly released.

Buying a **used** aircraft (`FleetEndpoints.BuyAsync`) uses the same scheduler, via `MaintenanceScheduler.ResolveUsedAircraftState`: a used airframe costs 55% of the new price but starts 70% of the way into both maintenance cycles and at 70% condition rather than 100% - the discount is repaid through an earlier trip to maintenance, not given away for free.

## Virtual pilots and wall-clock resolution: VirtualFlightResolverService

`VirtualFlightResolverService` is a second `BackgroundService`, alongside `EconomyClockService`, that resolves every virtual pilot's scheduled occurrence whose block time has elapsed on the real wall clock. It runs once immediately at startup and then every 60 seconds, deliberately reusing `EconomyClockService`'s idempotency/monotonicity/capped-catch-up shape rather than inventing a second pattern:

- **Idempotency is structural.** Each occurrence's `Flight` row (and whatever `LedgerTransaction` rows it produces) and the `EconomyState.LastScheduleResolvedUtc` watermark advancing past that occurrence commit in the same `SaveChangesAsync` call, occurrence by occurrence — a crash mid-catch-up loses at most the not-yet-committed remainder of the pass, never posts an occurrence twice and never silently drops one. `LastScheduleResolvedUtc` shares the same `EconomyState` singleton row `EconomyClockService` owns rather than a second watermark row; only `EconomyClockService` ever creates that row, so if this service finds it missing it does nothing that pass and picks it up on the next tick.
- **Strictly monotonic**, exactly like the monthly billing watermark: the resolved-up-to point only ever moves forward and never past the current clock reading; a clock reading before it is a backwards jump — nothing processed, watermark unmoved, logged rather than absorbed.
- **Capped catch-up, bounded two ways per pass**: at most 500 occurrences actually resolved, and the enumeration window itself never looks further ahead than about 400 days — so neither a huge schedule backlog nor an enormous apparent clock jump can produce an unbounded burst of completed flights in one pass. The remainder simply continues on the next 60-second tick.

**Resolving one occurrence.** For each pilot's schedule entry due since the watermark, the service first decides whether it's actually flyable — the assigned `FleetAircraft` must be `Active` (not `InMaintenance` or `InFlight`) and physically at the route's departure airport (a grounding whose downtime has already elapsed by the occurrence's own departure time is released first, same lazy-release principle as `MaintenanceReleaser`). If it isn't flyable **specifically because the aircraft is grounded for maintenance**, and the schedule's `AutoSuspendOnMaintenance` flag is set (the default), the occurrence is recorded as `FlightStatus.Suspended` instead — no ledger line under either playstyle, since the schedule isn't at fault for a check the simulation imposed. Resumption needs no code of its own: the very next occurrence for that schedule simply re-evaluates the aircraft's status again, and once it's released the occurrence resolves normally. Every other unflyable reason (wrong airport, still airborne), or a maintenance grounding with `AutoSuspendOnMaintenance` off, falls through to the ordinary path: the occurrence is recorded rather than silently dropped or teleported, and `EconomyConfig.UnflyableSchedule.CancellationFee` decides whether it's logged as **Skipped** (fee is zero — Casual) or **Cancelled** (fee is charged and posted as a `CancellationFee` ledger line — True-life), with the specific reason stored on the `Flight` row (`UnflyableReason`) exactly as it will read in the UI (for example, `"G-OLAF is still at EGPF from an earlier leg — this leg needs it at EGGD."`). The aircraft's position is never touched for an unflyable occurrence, suspended or otherwise.

If it is flyable, the occurrence is flown as a **full economic citizen** through the exact same `FlightEconomicsCalculator` → `FlightEconomicsPoster` → `MaintenancePoster` pipeline a player's manually-completed flight uses (`FlightEndpoints.CompleteManualAsync` is this code's closest relative, and is followed wherever the two overlap): it earns ticket revenue, pays every itemised cost including the pilot's salary share, advances the aircraft's airframe hours and location, wears its condition, and can trigger a maintenance grounding exactly like a player flight would. Landing quality and delay variance come from the pilot's `SkillRating` via the seeded PRNG rather than measured telemetry, and no aircraft-type mismatch check applies (there's no simulator loaded aircraft to compare against) — otherwise it is indistinguishable from a player-flown sector in the ledger and the flight record. **Player flights are never touched by this service** — it only ever reads `PilotScheduleEntry` rows, which a player pilot (`Pilot.IsPlayer`) can never own (enforced in `PilotEndpoints.SaveScheduleAsync`).

## Reputation and pilot skill

`Airline.ReputationScore` and `Pilot.SkillRating` are both live inputs — read by the demand and virtual-pilot-performance code respectively — that used to be written once at creation (50) and never mutated again. Each now has a pure, recomputable engine in `FSOps.Core`, and a single poster that every relevant call site shares, following the same "one call point, not three-plus copies" reasoning already established for `MaintenancePoster` (see [Maintenance scheduling](#maintenance-scheduling)).

**`ReputationCalculator` (`FSOps.Core.Economy`)** advances a score by exactly one flight's outcome via exponential smoothing toward a per-flight target, rather than recomputing from full history on every call:

- `AdvanceForCompletedFlight(currentScore, config, delayMinutes, landingFpm)` blends an on-time score (100 within a grace tolerance of 5 minutes, decaying linearly to 0 by 45 minutes late) and a landing score (mapped from the same best/worst-case fpm bounds `VirtualPilotPerformanceCalculator` uses, so a player's real touchdown and a virtual pilot's simulated one are judged on literally the same scale) at an 0.8/0.2 weight, then steps the current score toward that blended target by a fixed smoothing factor (`Alpha ≈ 0.013767`, derived so a run of maximum-scoring sectors crosses 75 at exactly the 50th sector). Either input can be `null` (an elevated simulation rate, or no captured touchdown) and is excluded from the blend rather than guessed at; if both are `null` there is nothing honest to score and the score is returned unchanged.
- `AdvanceForCancelledOrSkipped(currentScore, config)` steps toward a harsher target (0) at a steeper multiplier (2.5×) than any completed-sector outcome could produce, so a cancellation always costs more standing than merely running late — deliberately never called for `FlightStatus.Suspended`, which is not this calculator's business to know about at all; every caller is responsible for that exclusion.
- `AdvanceForUnverifiedManualCompletion(currentScore, config)` takes **no** timing or landing input at all, stepping toward a flat target at a small multiplier (1/3 of `Alpha`, ≈ −0.23 from a reputation of 50, against an ordinary sector's own worst-case −0.69). An earlier version of this path derived an on-time score from wall-clock time between start and manual completion — that was a real, shipped exploit, and is worth naming so it's never retried: a flight completed moments after starting reads as an enormous *early* arrival under that formula (the wall clock there measures how fast the player clicked a button, not how the sector went), which scored as a perfect sector and turned "start, immediately complete, repeat" into a reputation-and-revenue farm.

**`ReputationPoster` (`FSOps.Server.Services`)** is the shared call point — `PostCompletedFlight`, `PostCancelledOrSkipped`, `PostUnverifiedManualCompletion` — used by all three completion paths: `FlightLifecycleService`'s real-telemetry completion, `FlightEndpoints.CompleteManualAsync`, `FlightEndpoints.AbandonAsync` (which reuses `PostCancelledOrSkipped` unchanged — an abandoned sector never happened from a passenger's point of view, exactly like a skipped or cancelled one, and its lost ticket revenue/fuel is a separate financial consequence, never a substitute for the reputation cost), and `VirtualFlightResolverService`'s flown/unflyable paths. It is never called for `FlightStatus.Suspended` anywhere. Each call mutates the same tracked `Airline` instance the caller's own flight/watermark commit already saves in one `SaveChangesAsync`, so the update inherits that commit's existing idempotency guarantee (`Flight.RevenuePosted` for a player flight, the per-occurrence Flight-row/watermark commit for a virtual one) rather than needing one of its own.

**Every exclusion was checked in both directions.** Building this surfaced a durable lesson: a rule that excludes a flight from reputation must be checked for whether it can be used to *avoid a loss*, not only whether it can *manufacture a gain* — the first question is the obvious one, the second is where the exploits actually were (the manual-completion timing bug above, and the "just abandon it" escape hatch both came from this). Any future change to what's excluded from reputation should be re-checked the same way.

**`PilotSkillCalculator` (`FSOps.Core.Scheduling`)** derives `Pilot.SkillRating` from career hours flown and idle time since last flown — fully recomputed on every call from `(hoursFlown, lastFlewUtc, now)`, never incremented, so calling it any number of times for the same inputs can never move a pilot's skill twice:

- **Growth**: `1 - 0.5^(hoursFlown / GrowthHalfLifeHours)` fraction of the way from `StartingSkill` (50) to `SkillCap` (87, deliberately below perfect so variance never fully disappears) — a diminishing-returns curve with a 300-hour half-life, applied identically to every pilot including the player (harmless, since a player's own flights are always judged by real telemetry, never by this rating).
- **Idle decay**: only ever triggered by a nonzero gap between `lastFlewUtc` and `now`. `IdleGracePeriodHours` (336h = 14 days) must elapse with no flight before decay starts at all; beyond that, a half-life decay (`IdleDecayHalfLifeHours` = 720h = 30 days) pulls the rating back down toward `StartingSkill` — never below it. `VirtualFlightResolverService`'s periodic pass is the **only** caller that ever passes a nonzero idle gap, and it deliberately skips every `Pilot.IsPlayer` pilot — the player's own record never decays, by construction, not by a guard bolted on afterward. A pilot on a standing schedule keeps flying on the wall clock even while FSOps is closed (see [Virtual pilots and wall-clock resolution](#virtual-pilots-and-wall-clock-resolution-virtualflightresolverservice)), which keeps `LastFlewUtc` fresh regardless of real-world elapsed time — decay only ever reaches a pilot deliberately left with no schedule at all.
- `ComputeEarnedSkill(hoursFlown, config)` exposes the growth curve alone, with no decay applied, so the UI can show "earned 68 from experience, currently 61" rather than a smaller number with no explanation — see `pilotSkillStatus` in `src/fsops-web/src/lib/pilotSkill.ts`, which turns `PilotSummary`'s server-computed fields into one of five status tones (never-decays, never-flown, decaying, grace-warning, normal) for the Pilots page.

**Surfacing it.** `AirlineEndpoints.GetReputationAsync` (`GET /api/v1/airline/reputation`) backs the Dashboard's reputation card: current score, a direction (`improving`/`declining`/`steady`/`new`) derived by comparing the average of the last 15 sectors' *targets* (not their outcomes) against the current score with a small threshold so a single borderline sector can't flip the label, on-time percentage and cancelled/skipped counts over that same window, a landing-quality bucket (`smooth`/`firm`/`hard`), and the exact demand multiplier this score currently applies (`DemandCalculator.ReputationDemandMultiplier`, the same function `AvailablePassengers` itself calls, so the card can never quote a number the demand engine doesn't actually use). `src/fsops-web/src/lib/reputation.ts` turns that summary into plain-language driver sentences and the demand-multiplier line, deliberately omitting a driver the backend couldn't measure rather than showing it as a false zero.

**Config.** Every figure above lives in `economy-config.json`'s `reputation`/`pilotSkill` blocks (`EconomyConfig.Reputation`/`PilotSkill`, `FSOps.Core.Economy`) and the reputation-to-demand mapping in `DemandConfig` (`ReputationBaselineScore` = 50, `ReputationSensitivity` = 0.25, `ReputationFloor` = 0.3 — solved so reputation 100 gives exactly 1.25× and reputation 0 gives exactly 0.75× the baseline demand) — shared across playstyles, not one of the `casual`/`trueLife` override blocks.

## The weekly schedule builder: aircraft-per-duty-day

The first build of the schedule builder organised everything by pilot, and let each leg pick its own aircraft independently. That let two legs in the same pilot's day reference two different airframes and pass every check cleanly, because `PilotScheduleValidator`'s continuity/overlap checks group by `FleetAircraftId` - two legs on two different aircraft in one day were simply never compared to each other. The redesign closes this by construction rather than by adding another check to catch the symptom: `PilotScheduleValidator.ValidateDutyDayAircraftConsistency` runs first, before geographic continuity or anything else, and groups every proposed entry by `(PilotId, DayOfWeek)` - if more than one distinct `FleetAircraftId` appears in that group, the whole save is rejected with every offending registration named, before any of the geometry checks even run. One aircraft per pilot per duty day is now a structural invariant the API layer cannot construct around, not a convention callers are trusted to follow.

**What this changes for the caller.** `PilotEndpoints` exposes two option endpoints that mirror the builder's two-step flow: `POST /pilots/{id}/schedule/aircraft-options` lists every fleet aircraft with an `eligible`/`reason` pair (ineligible for being reserved-for-player or grounded, in that priority order, matching the same "hard blocker before a one-click fix" ordering `FlightEndpoints.OptionsAsync` uses - see [Aircraft reservation](#aircraft-reservation-the-two-way-gate-and-reservationreconciler)), and `POST /pilots/{id}/schedule/leg-options` lists which legs *that already-chosen* aircraft can fly next, from wherever it will actually be. A reserved aircraft never reaches `PilotScheduleValidator` at all - `leg-options` short-circuits every route to `illegal` with the reservation reason directly, rather than running full validation only to reject on the same fail-fast structural check `Validate()` uses for the `PUT /schedule` save.

**`GET /pilots/schedule/overview`** is the airline-wide, read-only counterpart: every fleet aircraft as a row, its legs across the week, resolved once from every pilot's saved schedule and grouped by aircraft (or, in the frontend's second tab, by pilot) rather than edited from here - editing stays exclusively in the per-pilot schedule view. This is what makes "is my fleet actually being used" answerable at a glance instead of requiring a pass over every pilot individually.

`PilotScheduleValidator.Validate` accepts a `requireWeekClosure` flag: `PUT /schedule` passes `true` because a saved week must genuinely repeat (Saturday's last leg on an aircraft must connect to Sunday's first leg on the same airframe, and a pilot's last duty day must get its rest before the first comes back around), while the options endpoints pass `false`, because a week under construction is legitimately unclosed - the closing pair is skipped, but every interior pair is still checked in full. `WeekMinutes` (10,080) is the shared cyclical unit both paths reason in.

## Aircraft reservation: the two-way gate, and ReservationReconciler

`FleetAircraft.ReservedForPlayer` used to be a soft preference - one aircraft flagged, everything else fair game to both the player and the virtual-pilot scheduler, with nothing arbitrating a genuine conflict between the two. It is now a hard, mutually exclusive gate, enforced independently on both sides so the conflict is structurally unrepresentable rather than merely discouraged:

- **`FlightEndpoints.StartAsync`/`OptionsAsync`** only ever offer the player a `ReservedForPlayer` aircraft - an unreserved one shows disabled with `"Not reserved to you - reserve it from the Fleet page to fly it."` and `StartAsync` refuses outright with the same reasoning if called directly.
- **`PilotScheduleValidator.Validate`** rejects any entry whose aircraft is `ReservedForPlayer`, structurally and fail-fast (before the aircraft-per-duty-day or geometry checks even run) - and, as above, the builder's own option endpoints never offer a reserved aircraft as a candidate in the first place, so a player normally never even sees the rejection.
- **`FleetEndpoints.SetReservationAsync`** (`PUT /fleet/{id}/reservation`) is the sole place the flag ever changes post-creation. Releasing (`Reserved: false`) always succeeds immediately - a reserved aircraft was never claimed by the scheduler, so there is nothing on the other side to conflict with, even if the aircraft is mid-flight right now. Reserving (`Reserved: true`) an aircraft that already has active `PilotScheduleEntry` rows is refused with **409 Conflict** by default, naming every offending leg (pilot, day, route); passing `ForceClearSchedule: true` soft-deletes those entries and reserves the aircraft in the same call, echoing back exactly what was cleared.
- **The single-aircraft case is explicit, not automatic.** `AirlineEndpoints.CreateAsync` reserves the founding aircraft directly. `FleetEndpoints.EnsureSoleAircraftIsReservedAsync` runs at the moment a second aircraft is about to be added (from both the lease and buy paths) and re-asserts that the existing sole aircraft is reserved if it somehow isn't - "the moment reservation actually starts to matter." Nothing else in the app ever re-forces the flag once a fleet exists; from there it is entirely the player's own choice.

**`ReservationReconciler`** (`FSOps.Server.Services`) is the one-time-per-boot repair for a contradiction the old soft-preference model could leave behind: a database where an aircraft is marked both `ReservedForPlayer` and has active scheduled legs, written before this rule existed. It runs on **every** startup (not once, like a migration - a permanent safety net, not just a one-off fix), in a scope created immediately after migrations apply and strictly before any hosted service starts, because `VirtualFlightResolverService` never itself consults `ReservedForPlayer` and would otherwise resolve a contradictory occurrence on its very first pass. The resolution rule is fixed: **the schedule always wins** - a contradictory aircraft has its reservation released (`ReservedForPlayer = false`); its schedule is never touched, since silently deleting legs the player built is not this code's decision to make. If releasing leaves an airline with zero reserved aircraft, the reconciler reserves a replacement that has no scheduled legs of its own (preferring one parked at the home base, then the oldest), rather than risk recreating the exact contradiction it just fixed; if every remaining aircraft has legs, the airline is deliberately left at zero and recorded in the result for later surfacing. A clean database produces an empty result and writes nothing. See [Troubleshooting](guides/troubleshooting.md#a-restored-save-had-an-aircrafts-reservation-released) for what this looks like to a player restoring an old save.

## Getting rid of an aircraft, and settling a loan: the quote-then-confirm pattern

Three actions - selling an owned aircraft, ending a leased one's lease early, and settling a loan (fully or by overpayment) - share a deliberate pattern across `FleetDisposalEndpoints` and `FinanceEndpoints.SettleLoanAsync`/`OverpayLoanAsync`: **a `GET .../…-quote` endpoint precedes each commit, and the commit recomputes the same figure from current state and compares it, bit-for-bit, against what the caller confirmed.** A sale value depends on airframe hours and condition, which a virtual pilot's background flight can move; a lease-termination charge depends on wall-clock time, which always keeps moving; a loan's outstanding balance can move if `EconomyClockService`'s billing tick posts a payment against it in the same window a confirmation dialog is open. All three actions are irreversible, so on any mismatch the commit endpoint returns `400 Bad Request` with the fresh figure rather than silently posting a different number than the one the player saw and clicked. All time reads go through `IClock`, not `DateTimeOffset.UtcNow` directly, so the drift itself is deterministically testable.

- **`AircraftDepreciationCalculator.ComputeSaleValue`** (`FSOps.Core.Finance`) derives a resale factor from `NewAircraftResaleFactor` (0.80) minus weighted terms for condition and average A/C-check cycle progress, minus a further penalty if the aircraft is currently grounded, clamped to a configured floor - applied to the type's playstyle-scaled purchase price. Buying then immediately selling is always a loss; flying first and selling costs more still.
- **`LeaseTerminationCalculator.ComputeSettlement`** charges a pro-rata amount for the fraction of the current 30-day billing period already used (from `EconomyState.LastProcessedUtc`, the same watermark `EconomyClockService` owns) plus a flat `FeeMonths`-of-rent early-termination fee, posted as two separate itemised ledger lines.
- **`LoanSettlementCalculator`** computes a full-payoff quote (`RemainingBalance` plus a `FeePercentOfRemainingBalance` early-settlement fee) and applies an overpayment (reduces `RemainingBalance` only - the monthly payment is deliberately left unchanged, so an overpayment always shortens the term rather than lowering the payment; this is the only one of the three actions with no separate fee, since the fee is scoped to closing a loan out completely).
- **Shared blocking rules** (`FleetDisposalEndpoints.EvaluateDisposalBlockersAsync`): wrong ownership kind for the action (sell needs `Owned`, end-lease needs `Leased`), never while `FleetAircraftStatus.InFlight`, and never while the aircraft is on a virtual pilot's standing schedule (named, rather than silently unassigned). Grounded-for-maintenance is deliberately **not** a blocker for either disposal action - a worse sale figure, not a refusal, is the correct handling; selling explicitly does **not** pay off any outstanding loan, which is against the airline's cash flow rather than secured on a specific airframe, and the quote states this plainly.

## The Finances page and the away-summary

**`FinanceEndpoints`** backs the Finances page. Every figure it returns that isn't explicitly named an estimate is summed straight from posted `LedgerTransaction`/`Flight` rows at request time - never a cached or recomputed total - so nothing on this page can ever disagree with what actually moved the cash balance, the same rule the rest of the app follows. The one deliberate exception is `PilotsAsync`'s `estimatedTotalCost`/`estimatedNetContribution`: `revenue` and `operatingCost` per pilot are real ledger sums (joined by `LedgerTransaction.FlightId`), but the comparison figure adds the pilot's `MonthlySalary` prorated to the requested window - and a prorated salary is never itself a ledger posting, since the real monthly wage line posts in full on its own cycle wherever that falls. The field names carry the `estimated` prefix specifically so the distinction survives into the frontend. `RoutesAsync` has no equivalent prorated cost (a route carries no monthly wage of its own), so every figure it returns is exact. `LeasesAsync`'s `nextPaymentUtc` is `EconomyState.LastProcessedUtc + EconomyClockService.PeriodLength` - a real rolling date, not a calendar-month assumption.

**`MaintenanceEndpoints`** backs two further things beyond the automatic accrual `MaintenancePoster` already applies at flight completion:

- **Perform maintenance now** (`GET /fleet/{id}/maintenance-quote`, `POST /fleet/{id}/perform-maintenance`) - the same quote-then-confirm shape as disposal. `MaintenanceScheduler.ApplyForced` always resets the chosen check's hours-since-check to zero regardless of how much of the interval had actually accrued, so bringing a check forward genuinely forfeits whatever hours were left; the quote shows the cost, downtime, hours remaining until the check would fall due naturally, and every affected schedule entry (pilot, day, route) before commit. Blocked while `FleetAircraftStatus.InFlight` or already `InMaintenance` - maintenance still never interrupts a flight in progress, and this endpoint is no exception to that rule.
- **The away-summary** (`GET /away-summary`, `POST /away-summary/acknowledge`) - everything resolved on the wall clock since `EconomyState.AwaySummaryLastViewedUtc`: ledger lines grouped by category, completed virtual-pilot flights (sectors/revenue/cost/net), maintenance events, and any flight recorded `Skipped`/`Cancelled`/`Suspended` in the window, with its reason. `GET` is deliberately side-effect-free (beyond a one-time bootstrap for a brand-new airline, so nothing is reported before anything could have happened) so polling or reloading mid-session never loses anything; only `POST /acknowledge` moves the cursor. A window shorter than a 5-minute threshold reports nothing, so a normal reload never trips it. The frontend's `AwaySummaryDialog` mounts once, app-wide, in `AppShell` rather than on any single page, so it surfaces on whatever route the player lands on first.

## The live operations map

`OperationsEndpoints.GetLiveAsync` (`GET /api/v1/operations/live`) backs the Dashboard's live operations map. It returns two things: every aircraft currently "in the air" (player and virtual, mixed together), and the airline's route network for the map's background arcs.

The player's own aircraft, if a flight is in progress, comes straight from `FlightLifecycleService.GetActiveSnapshot` — real telemetry, not interpolated, exactly as the Fly screen's own live view uses.

A virtual pilot's aircraft is never stored as "airborne" anywhere — it's computed fresh on every request from the schedule template plus the wall clock, which is what keeps it automatically consistent with `VirtualFlightResolverService`'s own eventual resolution (this endpoint never decides whether a flight is economically real; it only visualises where a currently-in-progress occurrence *would* be if it resolves the way its template says). For each schedule entry, `WeeklyOccurrenceCalculator` finds the most recent occurrence's departure time; if the block time (from `BlockTimeEstimator`, using the route's distance and the aircraft type's cruise speed) hasn't yet elapsed, the aircraft is airborne. Its position is interpolated along `GreatCircle.SamplePath` from the fraction of *airborne* time elapsed — taxi-out and taxi-in are deliberately excluded from the position fraction, so the aircraft sits at its departure or arrival airport while taxiing rather than sliding partway down the great circle before it's actually left the ground — with heading derived from the bearing to the next sample point, and phase mapped onto the same phase names `FlightPhaseStateMachine` uses so the two marker kinds read consistently on the map.

## How the SPA is chunked

Every page is loaded through `React.lazy` behind a single `Suspense` boundary in `App.tsx`, and the three components that mount MapLibre (`LiveOpsMap`, `RouteMap`, `LiveFlightMap`) are lazily loaded again inside their own pages. `vite.config.ts`'s `manualChunks` deliberately groups **only** `react`/`react-dom`/`scheduler` into a `vendor-react` chunk; a broader catch-all was tried and rejected, because it swept MapLibre into a statically-imported bucket and forced it to load eagerly again.

This matters for the in-game panel more than for the browser. MapLibre is by far the heaviest dependency in the app — roughly 800 kB raw on its own, over half the old single bundle's gzipped weight — and the panel is a small read-only view that never needs a map. Splitting it out took the eager first paint from about 425 kB gzipped to about 134 kB, and Fleet, Pilots, Finances, Statistics and Settings now never fetch MapLibre at all.

One honest caveat: the Dashboard's `LiveOpsMap` is gated on the live-operations request completing rather than on any user action, so MapLibre *is* fetched there shortly after the shell renders. It no longer blocks first paint, but the dashboard is not a map-free route.

Every lazy boundary needs a designed fallback, not a blank area — `PageSkeleton` for routes, and map-sized `Skeleton` blocks for the map components so nothing shifts when they arrive.

## Testing

**Backend:** `tests/FSOps.Core.Tests` and `tests/FSOps.Server.Tests` are xUnit, run with `dotnet test` from the repository root — see [Solution layout](#solution-layout) for what each covers.

**Node version:** the frontend tests need **Node 22 or newer** — jsdom's bundled `undici` calls `webidl.util.markAsUncloneable`, which does not exist on Node 20, and the failure is not a failing test but the whole Vitest run dying at import with zero tests executed. Worth knowing because the symptom looks nothing like the cause.

**Frontend:** `src/fsops-web` uses [Vitest](https://vitest.dev/) (native to Vite, so it shares the project's existing config rather than needing a second build pipeline), run from `src/fsops-web` with `npm test` (watch mode) or `npm run test:run` (single pass, what CI-style checks should use). Configuration lives directly in `vite.config.ts`'s `test` block: `jsdom` environment, `globals: false` (tests import `describe`/`it`/`expect` explicitly from `vitest` rather than relying on ambient globals), a setup file at `src/test/setup.ts`, and `restoreMocks: true` so a mock in one test can never leak into the next.

Test files sit beside the code they cover (`*.test.ts`/`*.test.tsx`, matched by `include: ['src/**/*.test.{ts,tsx}']`), not in a parallel directory — `src/lib/format.test.ts` next to `src/lib/format.ts`, `src/components/schedule/scheduleMath.test.ts` next to `scheduleMath.ts`, and so on. As of this writing that covers: pure formatting and date logic (`lib/format.test.ts`), the reputation and pilot-skill display helpers described above (`lib/reputation.test.ts`, `lib/pilotSkill.test.ts`), the schedule grid's layout maths and draft-entry state (`components/schedule/scheduleMath.test.ts`, `draftEntry.test.ts`), and the request-body/reset behaviour of four confirm-then-act dialogs (`components/finance/LoanRepaymentDialog.test.tsx`, `components/fleet/SellAircraftDialog.test.tsx`, `EndLeaseDialog.test.tsx`, `RenameAircraftDialog.test.tsx`).

The scope is deliberately narrow, not an oversight: the suite exists because two shipped bugs slipped past `tsc` and a compiling build — a "pay off loan in full" button that posted no request body to an endpoint requiring the confirmed figure, and a confirmation input that reset mid-keystroke because a `useEffect` depended on object identity rather than a primitive. Both are exactly the class of bug `tsc` cannot see (it type-checks each side of the API boundary independently, never that a request body actually matches what an endpoint expects) and a runner catches immediately. Coverage is aimed squarely at that class: request bodies sent to the API, dialog reset/state behaviour, and pure calculation logic. **There are deliberately no component-rendering or DOM-snapshot tests** — they were considered and rejected as breaking constantly while proving little; if the frontend test suite grows a rendering layer later, it will be a deliberate addition, not a default this project started with.
